Flujo obligatorio para modificar o anular una venta

Jonatan y encargados no modifican ventas confirmadas directamente. Generan solicitud y Administración aprueba.

1Error detectadoSe identifica venta mal cargada, anulación o diferencia.
2SolicitudUsuario operativo carga motivo obligatorio.
3En revisiónAdministración revisa venta, rendición y caja.
4AprobaciónSe acepta o rechaza el ajuste.
5AplicaciónEl sistema crea ajuste, no borra el original.
6NotificaciónDirección recibe aviso automático.
7AuditoríaQueda valor anterior, nuevo, usuario y motivo.

Reglas de la pantalla del fotógrafo

Se busca velocidad operativa y cero acceso a información sensible.

Solo datos propiosNo ve ventas ni comisiones de otros fotógrafos.
Venta bloqueada sin jornadaNo puede vender si no inició jornada asignada.
Sin edición históricaLuego de rendir, cualquier cambio requiere solicitud.
Comisión estimadaVisible por día, mes y año, sujeta a validación final.

Notas para el programador

Este HTML sirve para usabilidad. Para producción requiere backend, base de datos y permisos reales.

Backend requeridoLaravel, Node, Django o similar. El prototipo usa localStorage solo para demo.
Base de datos sugeridausers, roles, permissions, user_scopes, audit_logs, adjustment_requests, special_permissions, partner_access.
RBAC + ScopeNo alcanza con rol. También hay que restringir por ciudad, punto de venta y aliado asociado.
Soft delete obligatorioVentas, rendiciones y movimientos financieros no se eliminan físicamente.
Auditoría inmutableEl log de auditoría no debería poder ser editado ni eliminado desde la interfaz.
NotificacionesAdministración modifica un registro sensible → Dirección recibe notificación automática.
